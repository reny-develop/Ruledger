# Ruledger v1

**v1 が終わったと言える条件を定める。** 方式そのものは
[Rule-Derived Test Design](https://github.com/reny-develop/rule-derived-test-design) の
`doc/thesis.md` にあり、何が実測されているかは同じリポジトリの `doc/verification.md` に
ある。ここで書くのは、その思想を **証明するため**と、**他人に体験させるため**に、
最低限どの成果物が要るかだけである。以降 §n は thesis の節番号を指す。

**この文書は足場である。** thesis も verification.md も、これも、v1 が形になった時点で
消す。読者は証明と体験を Ruledger から受け取るのであって、検証の記録や作業用のメモを
読むのではない。思想は README で足りる。**残るのは README と、走る Ruledger だけである**
(後述「消すときに README が引き取るもの」)。

## 語

新しい語は作らない (§「決定済み事項」)。ここまでに紛れたものを、先に片付けておく。

| 使う語 | 何を指すか | 使わない語 |
|---|---|---|
| **ルールセット** | JSON で書かれた規則そのもの | 文書。README や thesis と同じ語になり、どちらの意味か文脈でしか分からなくなる |
| **状態パス** | 状態の中の場所。`assigned`、`log` | — |
| **状態の名前** | 初期状態からの来かた。`#2 = #1 + release(月)` | パス。状態パスと混ざる |
| **テスト設計** | Ruledger が出し、人が編集し、コミットするもの。受けているところでは「設計」と短く書く | 設計データ。thesis が取り下げた `galley` を言い換えただけで、同じものに名前が二つできる |

「文書」は日本語の散文にだけ使う。Rulealize の英語が JSON を document と呼ぶのは
基盤の既定であり、英語側では触らない。

## 足りないのは機能ではない

三つに分けると、欠けている場所がはっきりする。

| | |
|---|---|
| 思想 | 固まっている |
| 実測 | 済んでいる |
| 再現性 | **揃った。verification.md の表は `dotnet test verify/Ruledger.Verify.csproj` が全部出し直す。CI の設定は置いたが、まだ一度も動いていない** |

証明のために要るのは新しい機能ではなく、**再現可能性**である。第三者にとって、いまの
verification.md は「著者がそう言っている」以上のものになれない。数字を出し直せる物が
どこにも無いからである。**証明とは散文ではなく、走る測定である。**

体験のために要るのも機能ではなく、**題材と手順**である。§5.1 のループ——直す、走らせる、
差分を読む——を他人の手で回せるかどうかであって、道具の能力はもう足りている。

**思想のために新しく作らなければならない機能は、一つしかなかった。** §4.3.2 の走査——歩行が
合流するために見るべき状態パスを、ルールセットから機械的に求めること——である。試作では
その結果を人が読んで打ち直しており、「機械的に決まる」が人を経由して成立していた。
**これは書いた** (`ObservationScan`、受け入れ条件 2)。残りは全て、試作が既にやったことの
製品化である。

## 証明に最低限必要なもの

| | 成果物 | なぜ最低限か |
|---|---|---|
| **P1** | 観測に効く状態パスを求める走査。各入力のガード、パラメータ領域、`terminal.when`、`terminal.result` から読まれる状態パスの不動点 | 主張が人を経由している唯一の箇所である (§4.3.2)。これが無いと履歴を持つルールセットでは合流が一件も起きない |
| **P2** | 計測フィクスチャ一式。版の対、編集集合、設定 | verification.md が挙げる改変版は、どれも成果物である。無ければ数字は再現できない |
| **P3** | verification.md の実測を全て再生成する測定。CI で回る | **verification.md は消える。残るのはこの測定である。** commit ごとに測り直されるなら、「測った」は主張ではなく事実になる |
| **P4** | 計測対象を現実的な時間で回せる速度 | 将棋は一状態 50〜65ms で、20,000 状態が 20 分を超える。CI に乗らない測定は、再現可能性が無いのと同じである (後述「いま残っているもの」で決着) |

逆向きに決着させるものが二つある。

**§2.5 のルールセットの穴を拾う道具は、v1 では作らない。** 思想は「穴を指摘する」では
なく「全部並べる」で成立している。歩いて届かなかったことを根拠にしてはいけないことも
確定済みである。道具の不在は未達ではなく範囲外である。

**歩き方の他の設定でも差分と持ち越しが成立することは、論証のままでよい。** ただし設定を
変えた対照を一つ測れば論証が実測に変わる。安いので P3 に含める。

## 体験に最低限必要なもの

| | 成果物 | なぜ最低限か |
|---|---|---|
| **E1** | 入る道具。`dotnet tool` で入り、`rulealize restore` で語彙が揃う | ホストプログラムを一行も書かせないこと自体が体験の一部である |
| **E2** | テスト設計の形式 (後述) | 人が触れる面はここしかない |
| **E3** | 手順書。reversi の一行改変と、業務側の roster | reversi だけなら「ゲームの話」で退けられる。roster は §5 の体験と業務ドメインの証拠を兼ねる |
| **E4** | 正直な失敗表示。未到達と、持ち越し失敗の三分類 | これが無ければ、うまくいったときだけ気持ちのよい道具になる (§6.7) |
| **E5** | reversi 3,000 状態が数秒で終わること | 待たされる手順書は体験にならない |

手順書は **起きなかったことを数える。** テストケース 0 件、テストデータ 0 件、期待値の
計算 0 回、影響範囲の検討 0 回、`pass` への波及は思い出さなくても来た (§5.1)。これを
本文ではなく手順の結果として出せれば、思想は一度で伝わる。

**対象はルールセットを読める人である。ただしこれは思想の対象ではなく、最初の段の対象で
ある。** 基盤が新しいので、読める人はまだほとんどいない。読めることを条件にしたのでは
なく、最初の段がそこにあるというだけである (§5.5)。手順書はこの区別を書く。**条件だと
読まれれば、読む人のいない思想になる。**

## 同じ状態かどうかを、二つの意味で聞く

「同じ状態か」という問いは、道具の中で二度現れる。**聞いていることが違うので、答え方も
違う。** ここを一つにしようとしていたのが、§6.7 に穴が残っていた理由である。

| 場面 | 何で見るか | 問い |
|---|---|---|
| 歩いているとき | **状態パス** — 走査が出した観測項目の中身 | もうここに来たか |
| 持ち越しと差分 | **状態の名前** — `#0 + assign(ann, 月)` という来かた | どの場面のことか |

**歩行が中身で見るのは、そうしないと二度と同じ場所に戻らないからである。** 履歴を伸ばし
続けるルールセットでは、割り当てが元に戻っても履歴が違うので、丸ごと比べるかぎり別の状態
になる。実測では**合流が一件も起きず**、二つある `result` の片方が予算内で一度も観測され
ない。**これが P1 の役目であり、唯一の役目である。**

**歩けはする。** thesis §4.3.2 のとおりで、潰さなくても終局には届く。失うのは合流と、その
ぶんの網羅である。ただし合流しない歩行は一本の経路が予算の長さまで伸びるので、**歩行は
明示スタックで書く。** 再帰では 3,000 状態でスタックが壊れる。

**持ち越しと差分が来かたで見るのは、§6.7 の穴がそれで閉じるからである。** 中身で引くと、
状態に項目が一つ増えただけで全ての鍵が変わり、振る舞いが何も変わっていなくても編集が
全部落ちる。来かたは項目が増えても変わらない。編集が失われるのは、その来かたが歩かれ
なくなったときだけであり、それは「予算内で届かなかった」として既に表に出る (§4.3.3)。

**閉じることを実測した** (`reversi` / `reversi-counted`、予算 3,000、編集 20 件)。手数を
数える項目を足し、`terminal.when` にそれを読ませた版である。**状態の中身は 3,000 件すべて
別物になる**——試作が 20 件全部を失ったのはこれである——のに、**来かたで引けば 20 件とも
残る。** 差分は共通 2,999 件で、合法な入力も終局も一件も動かない。食い違う 2 件はどちらも
予算の際で着地先が変わったもので、これは合流の位置が変わったのであって規則が変わったの
ではない。**その区別は道具が出す** (「同定に使う項目が両版で違う」と差分が述べる)。

同じ鍵で thesis §4.5 の実測も再現した。勝敗の入れ替え (`reversi-swapped`) は共通 3,000 件・
変化 844 件で、変化は全部が終局の `result` である。置ける条件を厳しくした版
(`reversi-strict`) は共通 1 件・前だけ 2,999 件・後だけ 2 件。**試作が状態の中身で出した
数と一致する。**

この分割には副次的な効きがある。**走査が項目を多めに残しても、当たるのは歩行の戻りだけ
になる。** 走査はルールセットを読んで求めるので、書き込み先と値が同じ形に見える箇所では
潰さない側に倒してある。その代償が人の編集に届かなくなる。

## 分割の仕方は、テスト設計に現れない

ルールセットを複合と構成要素に分けることは、**一つのルールセットの書き方**であって、別の
規則ではない。同じ規則を一枚に書いても分けて書いても、**テスト設計は同じでなければ
ならない。** これは v1 の受け入れ条件である。

| | |
|---|---|
| 同じでなければならないもの | 状態の数、各状態で合法な入力、その着地先、終局と `Result`、未到達 |
| 違ってよいもの | 入力の名前だけ。複合は構成要素の入力を別名の下で提示するので、一枚なら `raise` が `req.raise` になる |

だから **Ruledger は複合をそのまま歩く。** 構成要素を単体で歩いて済ませることはしない。
単体のテスト設計は構成要素についての設計であって、全体の設計ではない。それで代用すれば、
**テスト設計が「どう分けたか」に依存してしまう。**

走査も同じ形で通す。複合は構成要素の状態を別名の下に持つので、その項目は構成要素の項目に
別名を前置したものであり、**どれが観測に効くかは構成要素自身の答えである。** 複合が自分で
足すのは、`held` の締めと `fires` と、自分の `terminal` だけである。

**そこで構成要素を丸ごと観測に入れてはいけない。** 複合が構成要素を読む唯一の形はレコード
として一つの鍵を読むことで、丸ごと入れると、誰も読まない項目まで観測に残る。一枚に書いた
版はそれを潰すので、**同じ規則が違うテスト設計になる。**実測した（`seating` / `seating-merged`
で、9 状態・合流 0 と 7 状態・合流 2）。だから鍵がリテラルのときは `別名.鍵` に絞る。鍵が
計算されているときは、どの項目か決まらないので丸ごと残す——一枚に書いた版でも、そこは同じ
だけ読むことになる。

**この受け入れ条件が見張っているのは、ルールセットの性質ではなく走査の粗さである。** 基盤
の側では複合は締めることしかできず、`fires` も一枚版と同じ状態に届くことが実測されている。
食い違うとしたら Ruledger が原因である。

**構成要素の文書は渡されなければならない。** 無ければ断る。複合のガードの合法判定は構成
要素のガードを通るので、文書が無いまま答えると、**項目の欠けた集合が、欠けている印も無し
に返る。**

## テスト設計

**正本はテスト設計であり、人が読む行指向の形はその表示である。v1 では表示を作らない。**
形式がそれを塞がないことだけを保証する。そして人も Ruledger も、同じテスト設計から
テストを実行する。

| | 要件 | 理由 |
|---|---|---|
| a | Ruledger が読み書きできる。状態の名前、設定、人の編集 | 差分と持ち越しがこの上に乗る (§4.5 / §6.7) |
| b | **来かたが復元できる。** 開始状態と、そこへ至る入力の列 | 人が手で実行するとき、これが手順そのものになる。状態の名前は、既にこれを持っている |
| c | 状態ごとに一まとまりで、順序を持って並ぶ | 行指向の表示へ落とせる条件である |
| d | 観測結果は生成物としてのみ入り、人が書き込める場所は選択だけ | 観測結果を手で書かせた瞬間、そこが唯一の誤りうる箇所になる (§4.3.4) |
| e | 未到達と持ち越し失敗が、テスト設計の中に残る | 報告がコマンドの出力だけなら、コミットされたテスト設計から消える |

形式は `ruledger/test-design/v1`。Rulealize が読み書きする JSON に揃える。基盤は既に
`rulealize/state/v1`、`rulealize/input/v1`、`rulealize/outcome/v1` を持っており、b が要求
する「開始状態と入力の列」は、その連なりそのものである。テスト設計がそれらを素材のまま
抱えれば、人が手で実行するときも Ruledger が差分で実行するときも、読む物は同じである。
**写し取る工程がどこにも要らない。** `ruledger/test-design/v1` として、四番目のスキーマを
置く。

**抽選のあるルールセットを最初から入れる。** blackjack のように次の状態が誰の決定でも
ないルールセットでは `GetOutcomes` の結果が観測の一部であり (§4.2)、テスト設計が
`rulealize/outcome/v1` を抱えられないと、b の復元がその種のルールセットで成立しない。
後から足せば状態の名前の形が変わる。

**テスト設計は、そのままテストランナーが読める素材である。** Ruledger は既にルールセットを
実行している (§6.5)。期待値を算出するには、その状態にその入力を適用して結果を見るしか
ないからである。だから具体値——状態と入力——は最初からテスト設計の中にあり (要件 b)、
**「テストランナー向けの出力」は追加で作る機能ではなく、既にある。** v1 で作らないのは、
特定のランナーへの変換だけである。

## 成果物

```
src/Ruledger        走査・歩行・観測・テスト設計の読み書き・差分・持ち越し (非公開)
src/Ruledger.Cli    dotnet tool `ruledger`  ← v1 で公開するのはこれだけ
test/               単体
verify/             計測フィクスチャと、実測を再生成する測定
doc/test-design.md  ruledger/test-design/v1 の仕様
doc/tutorial.md     体験の手順 (reversi と roster)
```

| | |
|---|---|
| `ruledger derive <ruleset>` | テスト設計を出す。既存があれば編集を持ち越し、持ち越せなかったものを必ず報告する |
| `ruledger diff <test-design> <ruleset>` | 前の版のテスト設計を新しい版に当てる。これが実行であり、回帰検出である (§6.5)。終了コードが CI での検証になる |
| `ruledger observe <ruleset>` | 歩行が合流に使う状態パスと、潰す状態パスを出す |

設定はテスト設計とともに記録される (§4.3.1)。**予算 3,000 状態、`GetValidInputs` が
一つの状態で試す候補の上限 10,000、`GetOutcomes` が一つの入力に返す上限 64** の三つである。

**歩き方は一通りに決めた。** §4.3.1 が思想の側で選ばないと述べた二つは、こう選んである。
合法な入力を順にたどり、**一本の経路を終局まで歩き切ってから一段だけ戻り、親に残った入力
を続ける。** 合流は状態に着いた時点で判定し、既に見た状態ならそこで折り返す——予算はそれを
数えず、未到達にも数えない。**選べる幅が一つしかないので、いま記録するものが無い。**
二つ目を足すときに記録する場所が要る (後述)。

## 受け入れ条件

1. verification.md が挙げる実測が、このリポジトリの測定として全て走る。**散文ではなく、
   走る測定が証明である**
2. §4.3.2 の走査に、人が一度も介在しない
3. reversi の手順書が、ホストプログラム 0 行・テストケース 0 件で、数秒で完走する
4. 持ち越せなかった編集は、三分類つきで必ず表に出る。**黙って既定値に戻る経路が、
   コード上に存在しない**
5. 同じルールセットを同じ設定で二度走らせると、出てくるテスト設計がバイト単位で同一である
6. 複合として書いたルールセットと、同じ規則を一枚に書いたものが、同じテスト設計になる
7. テスト設計から、状態ごとの行指向表示へ機械的に落とせる。**v1 では表示は作らない。**
   将来を塞いでいないことの確認である
8. 日本語の散文が全て消え、README だけで読めるようになっている

## v1 に入れないもの

thesis §6.6 が挙げる三つ——ルールセット以外の検証、視覚化と編集、承認の記録——に加えて、
次を入れない。

- **特定のテストランナーへの変換。** 素材はテスト設計に既にある (前述)。どの形に写すかは
  出力形式の問題であり (§6.6)、v1 で決める必要がない
- **カバレッジに相当する数値。** §1.4 で「数字で品質を代理しようとしたこと」が問題だと
  述べた以上、達成率のような数字を出した瞬間に同じ誤用が始まる。**出してよい数字は
  「予算内で届かなかった」だけである**
- **ルールセットの穴の検出** (前述)
- **人が合流の項目を指定する手段。** 機械が出す集合より狭く指定すると、観測できる差の
  ある二状態が合流し、歩行がその先を見ないまま「見た」と判断する。**機械の集合が下限で、
  人は下げられない**
- **並列化と、インクリメンタルな歩行。** 速度は E5 の範囲で足りる
- **公開ライブラリ API。** v1 で公開するのは CLI だけである

## 作る順と、公開の条件

P1 → テスト設計の形式 → P2 → P3 → E3 が最短である。P4・E4 は、この順のどこに入っても
構わない。

**公開は v1 の完了と同時である。段階公開はない。** 証明も体験も Ruledger を走らせる
ことで渡すものであり、日本語の散文は公開時に消えるので、v1 より前に公開すれば読む物が
何も無い状態になる。

## いま残っているもの

**残りはここだけ見れば分かる。片付いた行は消す。** 済んだのは P1〜P4、E1〜E5、
テスト設計の形式、差分と持ち越し、仕様書、受け入れ条件 2〜7 である。

| | 残っていること |
|---|---|
| 受け入れ条件 1 | 測定 55 件は全て走る。**CI の設定は置いたが、まだ一度も動いていない。** 一度緑になるまでは「commit ごとに測り直される」は設定であって事実ではない |
| 受け入れ条件 8 | **日本語の散文を消す。これは公開そのものであり、判断を要する** — この文書、thesis、verification.md、motivation.md、`CLAUDE.md` の書き直し。受け入れ条件 1 が事実になっていないうちは早い |
| 公開 | `dotnet tool install -g Ruledger.Cli` がまだ通らない。README とチュートリアルはそう書いてある (「まだ動かない」と断ってある) |

**P4 は測って決着した。速度は Ruledger の側では詰められない。** shogi は一状態あたり
GetValidInputs が約 41ms、合法な入力一つの適用が約 3.8ms で、一状態に約 31 の入力がある。
つまり **一状態の四分の三は「合法な入力それぞれをどこへ行くか確かめるために適用する」で
あり、それはテスト設計が書き留める三つ目の観測そのものである。** 書き留めるものを減らさ
ずに安くする方法は Ruledger の中に無い。JSON の解析は全体の 0.5% で、詰めても意味がない。
**だから shogi の行は CI に乗る予算で測る** (60 状態)。chess は 300 と 1,500 で測る。
「20,000 状態」は試作の数字であって、主張はその距離を必要としていない。

**測定は 55 件、約 3 分 40 秒。** 単体は 41 件、2 秒である。以前 4 分かかっていたのは編集
20 件を毎回積み直していたからで、固定して `verify/choice/` に置いたので一度歩けば済む。
